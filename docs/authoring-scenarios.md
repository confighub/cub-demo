# Authoring scenarios

A scenario is the complete definition of one demo: a `scenario.yaml` describing the fictional
company and its fleet, plus a `manifests/` tree holding each component's `component.yaml` and
Kubernetes manifests. `cub demo install` stores the definition in an org; `cub demo up`
converges the org to it. This document is the authoring reference: the schema is defined (and
further documented) in `internal/scenario/schema.go`, and the embedded scenarios under
`scenarios/` are worked examples — `workflows` (6 clusters, 3 components) is the best first
read, `meridian` (99 clusters, 19 components) the full-scale one.

## Start from an export

```
cub demo scenario export workflows ./myco
# edit ./myco/workflows.yaml and ./myco/manifests/...
cub demo plan ./myco/workflows.yaml       # offline: what it expands to
cub demo install ./myco/workflows.yaml    # store the definition in the active org
cub demo up                               # create the dataset
```

Component directories are resolved from `./myco/manifests/<dir>` first and fall back to the
embedded copies, so an export can delete every directory it does not change. The loader
rejects unknown fields, so a typo fails loudly with the field name.

Rules that bite if ignored:

- **`name` must be a valid slug and is org-global.** Every entity carries it as the
  `DemoName` label (the teardown key), and cluster/component names must not collide with
  another scenario's — the seeder refuses to adopt a space owned by a different demo. Two
  scenarios can share an org only if all their names are disjoint.
- **`context:` pins the scenario to one cub context.** Mutating verbs refuse to run when the
  active context differs. Always set it: it is what keeps `cub demo down` from firing into
  the wrong org.
- **Class order is promotion order.** The `classes:` list is the order change workflows
  promote through, and the first class's stage must stay gate-free (see workflows below).
- **Manifests are Go templates that must also be valid YAML** (they are stored in the org as
  AppConfig/YAML units). Quote any template expression that begins a scalar or a key:
  `version: "{{.Values.version}}"`, not `version: {{.Values.version}}`.

## scenario.yaml

```yaml
name: myco                # slug; the DemoName label and the <name>-platform / <name>-scenario prefix
context: myco-demo        # cub context pin (strongly recommended)
company: MyCo Group       # the fiction: feeds templates and target facts
domain: myco.example
cloud: aws                # recorded as the Cloud.Provider fact
```

**Dimensions.** `regions` (name, providerRegion, dnsZone, locality), `classes` (see below) and
`departments` (a list of names; the `shared` department is implicit and holds the platform
clusters — `departments: []` is a valid single-department fleet).

**Classes** are the environment tiers, in promotion order:

```yaml
classes:
  - {name: dev,  replicas: 1, logLevel: debug, size: small, dbClass: db.t3.micro, multiAZ: false, nodeCount: 3}
  - {name: prod, replicas: 3, logLevel: warn,  size: large, dbClass: db.r6g.large, multiAZ: true, nodeCount: 9}
```

The knobs (`replicas`, `logLevel`, `size`, `dbClass`, `multiAZ`, `nodeCount`) have no built-in
effect: they exist so `component.yaml` function arguments and manifest templates can reference
them (`{{.Class.Replicas}}`). `values:` adds free-form knobs, read as `.Class.Values.<key>`.

**Clusters** are generated by rules, listed explicitly, or both:

```yaml
clusters:
  kubernetesVersions: ["1.31", "1.32"]     # assigned deterministically per cluster
  rules:
    - {class: prod, department: shared,   count: {us-east: 3, default: 1}}
    - {class: prod, department: payments, count: {us-east: 2}}
  list:
    - {region: us-east, class: dev, department: shared, index: 9, nodeCount: 1}
```

Each rule makes `count[region]` clusters of one class for one department (`default` covers
unnamed regions). Generated names are `<region>-<class><n>` for shared clusters and
`<region>-<department>-<class><n>` otherwise; each cluster becomes a space plus an OCI target
with facts (`Facts.Cluster.KubernetesVersion` etc.) worth filtering on in the demo.

**Components** come in two lists — `catalog:` (platform, `Layer=platform`) and `workloads:`
(business, `Layer=workload`); the shape is the same:

```yaml
workloads:
  - name: storefront
    owner: retail-web           # the Owner label
    department: retail          # workloads only
    dir: workloads/storefront   # component directory under manifests/
    external:                   # cloud resources; each becomes a Crossplane unit
      - {kind: rds, name: storefront-db}   # kinds: rds, bucket, queue, cache
    placement:                  # union of rules; empty means every cluster
      - {departments: [retail], exclude: {regions: [sa-east]}}
      - {departments: [shared], classes: [dev, test], maxIndex: 1}
    liveStatus: none            # optional: do not paint live status at seed time
```

A placement rule selects clusters by the intersection of its non-empty fields (`classes`,
`regions`, `departments`, `maxIndex`); `exclude` removes matches; the component lands on the
union of all rules. `liveStatus: none` leaves a component's deployments unpainted so a
workflow's healthy gate is only ever opened by a play (the `workflows` scenario uses this).

**Story** is the deliberate imperfection, deterministic from `seed`:

```yaml
story:
  seed: 42
  liveStatus: {degradedPercent: 2, outOfSyncPercent: 1, progressingPercent: 2}
  unreleased: {percent: 2}      # deployments left with an unreleased head
  skews:                        # post-release changes on a selection of deployments
    - {component: catalog-api, unit: api, function: set-image-reference,
       args: [api, ":v3.8.1"], where: {regions: [ap-northeast], classes: [prod]}}
```

**Workflows.** A ChangeWorkflow names no component: each change order binds one at creation,
and the change order's own space supplies the component its stage selectors are narrowed by,
so one definition governs every component that rolls out the same way. The tool generates
one shared entity per distinct rollout shape, in the home space: components placed on every
class share `standard-rollout`, and a component placed on fewer classes gets a workflow
whose stages are exactly its classes (e.g. `rollout-uat-prod`) — the server refuses to
promote past a stage that selects no space, so shapes cannot be mixed. All are bases-first:
a `bases` stage holding the covered class bases, then one stage per class's deployments.
`prerequisites` sets the gates per deployment stage (keys are class names plus `final`;
values from `released`, `healthy`); absent keys default to `[released, healthy]`. The first
class must stay gate-free — its previous stage holds only bases, which release nothing and
report no health. `changeOrders` seeds rollouts in flight:

```yaml
workflows:
  prerequisites: {test: [released], prod: [released, healthy], final: [released, healthy]}
  changeOrders:
    - component: cert-manager
      slug: cert-manager-1-17-0
      description: "Bump cert-manager to v1.17.0"
      unit: controller
      function: set-image-reference
      args: [cert-manager-controller, ":v1.17.0"]
      landedThrough: test       # "bases" or a class name
      degrade: 1                # paint N of that stage's deployments Degraded (blocks the next gate)
  # disabled: true              # skip workflow and change-order seeding entirely
```

A seeded change order applies the function to the root base, promotes stage by stage through
`landedThrough`, releasing and painting healthy so the next stage's gates hold; `degrade`
then blocks the following stage visibly.

**Plays** are the scenario's presenter moves — see [Plays](#plays) below.

## component.yaml

One per component directory:

```yaml
units:                          # created in the root base, in order, one manifest file each
  - {slug: controller, file: controller.yaml}
release: {unit: controller, container: cert-manager-controller}   # what bump-image bumps
values:                         # template inputs for this component's manifests (.Values)
  version: v1.16.1
perClass:                       # functions applied to each class base
  prod:
    - {function: set-replicas, args: ["{{.Class.Replicas}}"], where: "Slug IN ('controller','webhook')"}
perRegion:                      # applied to every deployment, args templated per region
  - {function: set-string-path, args: [rds.aws.upbound.io/v1beta2/Instance, spec.forProvider.region, "{{.Region.ProviderRegion}}"]}
perCluster:                     # applied to every deployment, args templated per cluster
  - {function: set-string-path, args: [apps/v1/Deployment, spec.template.spec.containers.0.env.TXT_OWNER, "{{.Cluster.Name}}"]}
perVariant:                     # a local override on one named deployment only
  us-east-prod1:
    - {function: set-string-path, args: [apps/v1/Deployment, spec...limits.memory, 2Gi]}
protect:                        # protected paths, per class (survive merges from upstream)
  prod:
    - unit: api
      paths: ["apps/v1/Deployment:catalog-api/catalog-api-api:spec.template.spec.containers.0.resources.limits.memory"]
      variants: [us-east-prod1] # optional: only these deployments; empty = base + all of the class
```

The design principle: **manifests are rendered once, for the root base**; all class, region
and cluster variation is applied by ConfigHub functions, so every difference is real recorded
history (revisions with provenance), not templating. Prefer a function over a template
wherever both would work. Functions are the server's vocabulary (`set-replicas`,
`set-env-var`, `set-string-path`, `set-image-reference`, …); `where` narrows the units a call
touches within the selected spaces. `perVariant` names no clusters of other scenarios — a
name that matches nothing is skipped with a note, so a shared component directory works
across scenarios of different sizes.

## Template contexts

Three different places take Go templates, with three different contexts:

| Where | Context |
|---|---|
| Manifest files | `.Scenario` (Name, Company, Domain, Cloud, the dimension lists), `.Component` (the component name), `.Values` (component.yaml values). External-resource templates additionally get `.Name` (the external's name). |
| Function `args` in component.yaml | `.Scenario`, `.Class`, `.Region`, `.Cluster` (Name, Region, ProviderRegion, Class, Department, Index, KubernetesVersion, NodeCount) — whichever the list is keyed by is populated. |
| Play steps | `.Scenario`, `.Home` (the `<name>-platform` space), `.Context`, `.Base "component"` (its root-base space), `.Workflow "component"` (home/slug of the shared workflow its change orders bind), plus variables earlier steps exported: `.Version`, `.PreviousVersion`, `.Var "name"`. |

And again: the manifest files must stay valid YAML with the templates in place — quote
expressions that begin a scalar or key.

## Plays

A play is a named sequence of steps, run with `cub demo play <name>` (no name lists them;
`--dry-run` prints without running). Steps run in order with `CUB_CONTEXT` pinned to the
scenario's context; the first failure stops the run. This is the tool/scenario boundary: the
tool ships four generic primitives, and every demo-specific actor ("ci", "argobot", an
outage) is a play the scenario composes from them.

A step is either a shell line or a primitive call:

```yaml
plays:
  ship:
    - call: bump-image
      with: {component: catalog-api, strategy: minor}
    - call: changeorder
      with: {component: catalog-api, description: 'catalog-api {{.Version}}'}
    - run: cub changeorder list --space {{.Base "catalog-api"}}
```

The primitives, with their `with:` parameters (unknown keys are rejected, naming the typo):

- **`observe`** — write a live-status observation on selected deployment spaces. Selectors:
  `component`, `variants` (cluster names), `stage` (+ `changeorder` as `space/slug` when the
  component has several in flight). `when: release-newer` observes only spaces whose release
  is newer than their last observation and reports them Synced/Healthy — a delivery bot
  (`force` re-reports regardless). `health: Degraded|OutOfSync|Progressing` with `message`
  paints an incident; no `when`/`health` means heal: repaint the selection healthy.
- **`invoke`** — run one ConfigHub function against one unit: `space`, `unit`, `function`,
  `args`, `change-desc`. The generic change-making move.
- **`bump-image`** — read the component's current image tag (from its `release:` block),
  bump it (`strategy: major|minor|patch`, or explicit `version`), write it back with
  `change-desc`. Exports `.Version` and `.PreviousVersion` for later steps.
- **`changeorder`** — create a change order in the component's base, bound to the shared
  workflow matching its class coverage: `component`, `slug` (defaults to
  `<component>-<version>` from an earlier bump-image), `description`. Refuses a slug that
  already exists.

Write plays so they run twice without a teardown: derive slugs from bumped versions rather
than hard-coding them, and let `observe` defaults heal what an incident play painted.

## Checking your work

- `cub demo plan <file>` — offline expansion: cluster table, component × class matrix, entity
  totals. Wrong counts show up here, before any server call.
- `cub demo install <file>` then `cub demo up --dry-run` — what would be created.
- `cub demo status` after `up` — per-phase have/want against the definition.
- Re-running `up` must be a no-op ("0 created or completed"); if it is not, something in the
  scenario produces unstable output.
- `cub demo play <name> --dry-run` — every step rendered, nothing run.
